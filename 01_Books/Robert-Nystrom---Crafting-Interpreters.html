Crafting Interpreters

Robert Nystrom - Crafting Interpreters

One-sentence thesis

The way to understand programming-language implementation is to build two complete interpreters — first a tree-walking AST evaluator in Java for clarity, then a single-pass bytecode VM with garbage collection in C for speed — for the same toy language (Lox), so the reader sees both the elegant pedagogical design and the gritty performance engineering of real interpreters, and the formal abstractions of computability cease to be magical because the reader has typed every line of the machine that realises them.

Why this book matters

The clearest, most patient, and most modern textbook on programming-language implementation. Where mid-century texts (Aho-Sethi-Ullman Dragon Book, Appel) treat compilation as a separate art accessible only through formal study, Nystrom shows that the entire pipeline — lexing, parsing, AST design, tree-walking evaluation, bytecode design, single-pass compilation, mark-and-sweep GC, closures, classes, inheritance — is buildable in two sustained projects, with every line of code shown and explained, and no step left as an “exercise.” Both interpreters fit in roughly 5,000 lines of clean, hand-typed code (jlox in <2,000 lines of Java per Part II’s preamble; clox is larger by Part III). For Yang’s purposes, the book is a constructionist (in the Papertian sense) treatment of the formal-machinery Minsky textbook abstracts: you can hold both projects in your head simultaneously and the formal results — that an interpreter is itself an Effective Procedure, that a Universal Machine can be built out of mundane parts — stop being mysterious.

The book also sits at the intersection of several traditions Yang’s wiki cares about. It is the constructional counterpart to Dijkstra’s derivational program-construction stance (Edsger W. Dijkstra - A Discipline of Programming); it is a worked example of the Ousterhout design ethic (deep modules, clean interfaces) applied to a non-toy system; it is the runtime layer that the Bryant-O’Hallaron textbook stops below; and it is the data-structures-in-anger companion to Marcello La Rocca - Grokking Data Structures (every data structure in the clox VM — dynamic array, hash table, linked list of upvalues, GC worklist — is implemented from scratch with measurable consequences). Reading Crafting Interpreters alongside any one of these books is more useful than reading either alone.

Core argument

  1. The right way to learn interpreter implementation is to build one, end to end, line by line, with no skipped corners (chs. 1, “Introduction”; ch. 2, “A Map of the Territory”). Nystrom states this explicitly — theory has its place but he learns by doing, and the book is structured so a reader who types every line will finish with a working language. No // TODO: implement this markers, no “we leave this to the reader,” no dependency on parser generators. Lex and Yacc are deliberately rejected in ch. 1 because using them hides the very mechanics the book exists to teach.
  2. There are two natural designs for an interpreter, each illuminating different things. Building both is what makes the pedagogy work:
    • Tree-walking interpreter (jlox, Part II, chs. 4–13). A recursive-descent Java parser produces an AST; an evaluator visits AST nodes recursively (the visitor pattern is the design exhibit). Slow, but every step of execution is a method call you can step into in a debugger. This is the clarity implementation.
    • Bytecode VM (clox, Part III, chs. 14–30). A single-pass Pratt parser emits a flat array of bytecode instructions (Chunk); a stack-based VM with manually managed memory and a precise mark-and-sweep garbage collector executes them. Fast (Nystrom’s clox runs Fibonacci ~30× faster than jlox in his benchmarks; ch. 14 motivates the rewrite by exhibiting jlox’s fib(40) as “achingly slow”). This is the performance implementation.
  3. Building both, for the same source language (Lox), reveals what changes and what stays invariant under different implementation choices. The semantics — Lox the language — are fixed across both halves; the engineering — Lox the implementation — varies. This invariance/variance split is itself an argument: it operationalises the difference between language and implementation that ch. 2 opens with by quoting Wirth’s distinction. Yang can read this as a long, worked-out lesson in what is essential vs incidental in any complex system, not just interpreters.
  4. The progression is additive: each chapter adds exactly one feature (variables, control flow, functions, closures, resolving and binding, classes, inheritance — and on the clox side, additionally hash tables, the GC, method dispatch, superclass chains, and final optimisations). Nothing is left as an “exercise,” and at every chapter’s end the resulting program runs. This is Crafting Interpreters’ most underrated technical achievement: Nystrom designed the chapter sequence so that no later chapter ever requires retrofitting an earlier one. Every reader’s running program at the end of chapter N is a strict superset of their program at chapter N-1.
  5. By the end the reader has built, with their own hands: (a) a recursive-descent parser + a Pratt parser; (b) a tree-walking evaluator implementing the Visitor pattern; (c) a single-pass bytecode compiler; (d) a stack-based VM with frame-relative addressing; (e) a precise mark-and-sweep garbage collector with tri-colour abstraction (ch. 26); (f) a hash-table based class/method dispatch system with inline caching; (g) closures via upvalues that capture either stack slots (open) or heap-allocated cells (closed) — Nystrom’s Lua-derived design; (h) inheritance via copy-down method tables. These are precisely the skills any serious interpreter or compiler implementer needs. None are exotic; all are what production VMs (CPython, Lua, V8’s interpreter tier) actually do.
  6. The pedagogical claim is general, not interpreter-specific. Nystrom’s introduction frames the book as a worked example of building beats reading for understanding, applicable to any complex system. This puts him in direct lineage with Papert’s Mindstorms (the Object-to-Think-With is the Lox interpreter) and Knuth’s Literate Programming (the prose-and-code interleaving is itself a model). The argument is not “interpreters are special”; the argument is “interpreters are an unusually good vehicle for the more general lesson.”

The diagram reads top-down: the book’s pedagogical thesis (build to understand) is operationalised by holding the language constant and varying the implementation; the variation reveals the two natural points in design space (tree-walk and bytecode); each implementation is constructed feature-by-feature in additive chapters; the cumulative effect is that abstract results from theory of computation cease to be abstract.

Key concepts

  • Tree-walking interpreter — direct recursive evaluation of an AST via the Visitor pattern; pedagogical baseline. A concrete instance of Effective Procedure machinery realised in Java. Nystrom’s jlox is a ≤2,000-line existence proof.
  • Bytecode VM — compiled-to-bytecode, stack-based execution of a flat instruction array; the design used by CPython, the JVM bytecode tier, V8’s Ignition, Lua. Frame-relative locals, single-pass compilation, no separate IR. The clox design.
  • Pratt parser (top-down operator precedence) — handwritten parser technique Nystrom calls “oral tradition” (ch. 17): a parselet table indexed by token type, each carrying prefix and infix functions plus a precedence level. Handles prefix/infix/postfix/mixfix uniformly; the parsePrecedence(precedence) driver is the entire parser core in clox. Nystrom argues this is the most underrated technique in compilers because academic curricula focus on generated parsers (LR, LALR) instead of hand-rolled ones.
  • Mark-and-sweep garbage collection — automatic memory management; one of the substantive technical contributions of Part III (ch. 26). Reachability defined operationally as “could possibly be read in the future”; roots are stack slots, globals, and a handful of VM-internal references; the worklist algorithm sweeps from roots and frees what it doesn’t mark. Nystrom implements precise GC (the VM knows exactly which words are pointers), not a conservative one.
  • Closure / upvalue — lexically captured variable; Nystrom’s clox design (ch. 25, “Closures”) uses Lua’s upvalue representation, which represents a captured local as either open (still living on the stack while the enclosing function is active) or closed (the value has been hoisted to a heap-allocated cell when the stack frame returned). This is a design Yang has not seen presented as cleanly elsewhere.
  • Single-pass compilation — emit bytecode directly while parsing, with no intermediate AST. clox does this; the implication is that backpatching (for forward jumps in if/while) is unavoidable and is solved with a small fixup pattern (ch. 23, “Jumping Back and Forth”).
  • Visitor pattern (double dispatch) — Java AST traversal pattern in jlox (ch. 5, “Representing Code”); the canonical resolution of the expression problem in OO languages without pattern matching.

(Concept notes for Tree-walking interpreter, Bytecode VM, Mark-and-sweep GC, and Pratt parser are deferred to a future PL-implementation book; promotion criterion is ≥2 source books.)

Key arguments created from this book

  • Building beats reading for understanding implementation — strong constructionist statement specific to programming-language theory; generalises to other systems but Nystrom argues it most explicitly for interpreters.
  • Hand-rolled parsing (Pratt) is undertaught relative to its production importance — academic-vs-industry mismatch claim (ch. 17).
  • A single-pass compiler with no IR is an underrated design point — most modern textbooks assume a multi-pass pipeline; Nystrom shows the single-pass design is enough for an entire dynamic language with closures, classes, and GC, at the cost of some ergonomic complexity in the compiler.

Best chapters/pages to actually read

The book has 35 chapters across an Introduction (ch. 1), a meta-tour (“A Map of the Territory,” ch. 2), the Lox sketch (ch. 3), Part II/jlox (chs. 4–13), and Part III/clox (chs. 14–30). The natural reading orders depend on goal:

  • For the conceptual map only (≈4 hours). Ch. 1 (“Introduction”) + ch. 2 (“A Map of the Territory” — the canonical scanning→parsing→analysis→IR→optimisation→codegen→VM/runtime tour) + ch. 3 (“The Lox Language”) + ch. 4 (“Scanning”) + ch. 5 (“Representing Code” — the visitor pattern derivation) + ch. 7 (“Evaluating Expressions”). Stop after ch. 7 if you only want to know what an interpreter is without building one. Ch. 2 alone is the best 25 pages of “what a compiler is” prose in print.
  • For jlox (≈30–40 hours typing through everything). Add chs. 6, 8–13 (parsing expressions, statements and state, control flow, functions, resolving and binding, classes, inheritance). At ch. 13 you have a complete, working scripting language with classes and inheritance, in <2,000 lines of Java.
  • For the bytecode story (≈40–60 hours, assumes you’ve done jlox). Part III, especially: ch. 14 (“Chunks of Bytecode” — instruction encoding), ch. 15 (“A Virtual Machine” — the dispatch loop), ch. 17 (“Compiling Expressions” — the Pratt parser is genuinely beautiful), ch. 20 (“Hash Tables” — the cleanest pedagogical hash-table-from-scratch in print), ch. 25 (“Closures” — open/closed upvalues), ch. 26 (“Garbage Collection”), ch. 30 (“Optimization” — NaN-boxing and superinstructions). Skip ch. 24 (“Strings”) on first pass; intern-table mechanics matter only after GC is in place.
  • For all of it. Read straight through. The book is engineered so each chapter is one self-contained step.
  • Skip on first pass — appendices (chs. 36–38) and the explicit acknowledgements/welcome chapters; the meta-essay quality of ch. 13 (jlox finale) is rewarding but not load-bearing. Anyone tight on time can skim chs. 5 (data regulation analogue: visitor pattern boilerplate) once they understand the pattern.

Important examples / cases

  • The Lox language itself. A small dynamically-typed object-oriented language with classes, single inheritance, closures, and managed memory. C-family syntax. Designed by Nystrom specifically for the book; small enough to teach, rich enough to need the full interpreter machinery (ch. 3).
  • The visitor pattern in Java for AST nodes (ch. 5). Concrete worked example of double dispatch and how it solves the expression-problem class of design problems. Useful even outside interpreter contexts; Yang has used the same pattern in research-data pipelines for AST-shaped data.
  • The single-pass Pratt-parser-plus-emitter in C (ch. 17). Nystrom shows how a Pratt parser combined with bytecode emission can compile and execute in one source-file pass without a separate IR. The clox compiler is a single 1,400-line file.
  • The hash table from scratch (ch. 20). Open addressing, linear probing, tombstones. One of the cleanest from-scratch hash-table treatments in print; Yang’s mental model of dict/HashMap in higher-level languages comes partly from this chapter.
  • The mark-and-sweep GC in C (ch. 26). Tri-colour abstraction (white / gray / black); explicit worklist; no generational, no write barriers, no moving — Nystrom keeps the GC at the precise level of complexity required for Lox’s semantics and no more. A model of pedagogical scope-discipline.
  • Closures via upvalues (ch. 25). The open/closed distinction (capturing-from-stack vs hoisted-to-heap) is the key idea; Nystrom motivates it from the cost of naïve heap-allocated environments.
  • NaN-boxing as the final optimisation (ch. 30). Pack 64-bit doubles, integers, booleans, nil, and object pointers into a single 64-bit Value by using the unused bits in IEEE-754 quiet-NaN payloads. Halves memory pressure on Value arrays. The optimisation is the book’s last chapter precisely because it presupposes everything else.

Critiques and limitations

  • Lox is not a real language. Production language design (Rust, Swift, Zig) involves enormous additional concerns (rich type systems, ownership, async/concurrency, FFI, package management, debugger protocols) that Nystrom intentionally omits. Building Lox does not equip you to design Rust.
  • Single-pass bytecode design is dated for production work. Modern VMs (V8 HotSpot, the JVM tiered JIT, GraalVM) use multi-tier JITs with extensive intermediate representations and speculative optimisation. Nystrom’s single-pass approach is pedagogical, not production. A reader who finishes clox is one or two large books away from understanding a JIT.
  • No type theory. Nystrom does not engage with type systems, parametric polymorphism, type inference, gradual typing, or the Curry-Howard correspondence (he name-drops it in ch. 1 then never returns). For that, Types and Programming Languages (Pierce) is the next book; reading Nystrom alone leaves the static-analysis chapter (ch. 11) feeling under-developed.
  • C and Java implementation choices are pedagogical, not idiomatic. Real C codebases differ in error handling (Nystrom uses exit() liberally), build systems (single Makefile), and module organisation (clox is a flat directory of .c files for ease of reading); idiomatic production C/C++ would use distinct compilation units, explicit error returns, and a vendored allocator. The book is meant for reading, not extending.
  • The GC has known pedagogical compromises. No generational collection; no incremental marking; no write barriers (a deliberate Lox-semantics-driven simplification — Nystrom calls it out). A reader who finishes ch. 26 must read further (Wilson’s Uniprocessor Garbage Collection Techniques; The Garbage Collection Handbook by Jones, Hosking, Moss) before designing a production GC.
  • Performance claims are anecdotal, not benchmarked rigorously. “30× faster than jlox” comes from fib(40) runs; comparisons across architectures, hosts, and competing language runtimes are not given. Yang would not cite a clox benchmark in a paper.
  • The chapter sequence is a strict line; alternative readings are not supported. A reader who wants to skip closures cannot easily skip ch. 25; a reader who wants to skip classes cannot skip chs. 27–29. The book’s additivity property is also its rigidity property.
  • Almost no engagement with the parsing-research literature. Earley, GLR, packrat parsers, parser combinators, PEGs, ALL(*), and tree-sitter are absent. A reader who finishes the book and tries to parse a real-world language will hit the limits of recursive-descent + Pratt within days.

Links to other books

  • Pedagogically constructionist version of Marvin Lee Minsky - Computation Finite and Infinite Machines — Minsky’s textbook proves that universal computation is achievable in many formalisms; he names the Universal Machine and develops the formal layer. Nystrom shows you how to build one in C in 5,000 lines. The two together are the formal-and-constructional pair: read Minsky for the proofs (“interpreters compute the same class as Turing machines”), read Nystrom for the experience of typing the interpreter into existence. The Halting Problem is the obvious result that, given Nystrom’s clox, Yang can now run on Lox programs and experience (e.g., a while (true) {} loop is exactly the input the formal result says cannot be decided).
  • Implementation companion to Edsger W. Dijkstra - A Discipline of Programming — Dijkstra gives the derivational perspective (a program is the residue of refining a specification under the rules of a calculus). Nystrom gives the constructional perspective (a program is the residue of typing it line by line and watching it run). Together they are the two halves of the implementation pedagogy. Reading them in sequence is unusual but rewarding: Dijkstra primes the reader to think about why each line of clox has the postcondition it does; Nystrom shows a system at the scale where Dijkstra’s calculus would be impractical.
  • Design-philosophy companion to John Ousterhout - A Philosophy of Software Design — Ousterhout argues for deep modules (small interfaces, large internal complexity) and strategic vs tactical programming. clox’s VM, Compiler, and GC modules are textbook deep modules in Ousterhout’s sense. Reading Ousterhout’s prescriptions and Nystrom’s constructed system back-to-back is an unusually clean check on Ousterhout’s claims: the prescriptions are visibly satisfied, and the violations (e.g., the compiler’s tight coupling to the chunk it’s emitting into) are the places where Lox’s semantics push back against design purity.
  • Data-structures-in-anger companion to Marcello La Rocca - Grokking Data Structures — La Rocca presents data structures abstractly with reference implementations. clox is the applied counterpart: every data structure La Rocca discusses (dynamic array, hash table, linked list, stack) is implemented from scratch in clox under realistic constraints (the GC needs to traverse them; the bytecode dispatch loop needs them to be cache-friendly). Reading them together turns abstract DS performance characteristics into design choices Yang can feel.
  • Runtime-layer companion to Randal E. Bryant and David O’Hallaron - Computer Systems A Programmer’s Perspective — Bryant-O’Hallaron stops at the level of “here’s how the linker, loader, and OS interact.” Nystrom’s clox is precisely the next layer up: the user-space VM that sits on top of the C runtime and the OS. Reading CSAPP first and then clox gives a continuous chain of abstraction from transistors to garbage-collected closures. This is one of Yang’s more useful reading-stack assemblies.
  • Direct Papertian heir — Crafting Interpreters is the kind of Object-to-Think-With (the Lox interpreter) and Microworld (the constructed clox VM) that Papert’s Mindstorms argues for, applied to adult learning of programming-language theory. The book is itself an exhibit of Constructionism applied to a domain (PL implementation) that academic curricula have tended to teach formally instead.
  • Aesthetic kin to Dennett — Dennett’s intentional stance and Nystrom’s prose-and-code interleaving share an aesthetic: explain by exhibiting the simplest mechanical realisation of a phenomenon, paraphrase the formal layer in human voice, and trust the reader to integrate. The two voices are different, but both books treat the reader as an apprentice.
  • Distant cousin to Mathematical Aesthetics and Falsifiability — Nystrom’s claims are not falsifiable in the Popper sense, but the book’s commitment to “every line shown” makes it falsifiable in a weaker, software sense: a reader who types every line and finds the result does not work has falsified the chapter. This is a rare property in textbooks.

Open questions

  • Does the two-implementation pedagogical pattern generalise beyond interpreters? The “build it twice — once for clarity, once for performance” pattern could plausibly apply to databases (a tree-walking SQL evaluator vs a vectorised execution engine), OSes (a monolithic kernel vs a microkernel for the same syscall surface), and distributed systems. Where else does it work? Where does it break down because the clarity and performance designs do not actually share semantics?
  • What is the right next step after Lox? A reader finishing Crafting Interpreters knows how to build interpreters but not how to design languages. Bridges to Types and Programming Languages (Pierce, 2002), Engineering a Compiler (Cooper-Torczon), and the LLVM tutorials are non-obvious; a Nystrom-style follow-up on type systems would be valuable.
  • What does a Pratt parser cost in maintenance vs an LR-generated parser? Nystrom claims hand-rolled Pratt is industry standard; production data on parser-related bugs in handwritten vs generated parsers across language ecosystems would either confirm or undercut this.
  • Is the additive-chapter structure a one-off feat or a transferable book design? Few technical books achieve it. What were Nystrom’s specific design moves to make it work, and could those moves be codified?
  • How does Lox compare to other “teaching languages” (Scheme, Pyret, Racket’s How-to-Design-Programs sub-languages, MIT/GNU’s STk) in pedagogical mileage per concept? Anecdotal evidence suggests Lox is unusually high-mileage; a structured comparison would be useful.

Research uses

  • Skill capability for AI tooling. AI agents that read and write code (Claude included) have to model how programs are executed, not just how they look. Building an interpreter is one of the cleanest ways to internalise this — useful for evaluating AI code-generation behaviour and for designing better prompts about runtime semantics. After clox, Yang has a mental model of “what the interpreter does on this line of Python” that survives prompt-engineering edge cases.
  • Constructionist learning model. The book is itself an argument for Constructionism applied to abstract domains. Useful as evidence in conversations about AI-tutor design or pedagogy: a Lox-style staged-construction tutor for any complex topic (statistics, probability, microeconomics) would, if Nystrom’s claim generalises, outperform a textbook-style explanation.
  • Personal craft. For any project that involves DSL design (config formats, query languages, simulation languages, the small custom languages Yang has written for research scripts), this book is the right starting point. Cleaner than Aho-Sethi-Ullman; more practical than the theoretical PL textbooks. The Pratt parser in ch. 17 alone is worth the price of admission.
  • Reading code by professional programmers. clox is one of the few production-quality C codebases written explicitly to be read. Yang can re-read clox at the line level when he wants to refresh his sense of what idiomatic, well-organised C looks like — closer to how a pianist re-reads scores than how a programmer skims documentation.
  • Mental model for performance tradeoffs. The jlox-vs-clox split is a worked exhibit of what one pays for clarity. Yang can apply the same diagnostic to his own code: “is this the jlox version or the clox version of this problem?” The question is unusually useful for prioritising rewrites.

What I would miss if I only read this note

The actual code. Crafting Interpreters is a code-rich book — every line is shown and explained, and reading it is partly a meditation on coding style (Nystrom’s prose-and-code interleaving is itself a model). The note tells you what you’ll learn; the book is the only way to actually learn it. Also missed: Nystrom’s distinctive voice — patient, self-aware, willing to make pedagogical sacrifices for clarity, and unembarrassed about engineering trade-offs. The book reads as a master craftsman talking to an apprentice. Specific things only present in the source:

  • The marginalia and “challenges” at chapter ends (small extension exercises with hints), which together constitute a second, parallel curriculum the note completely omits.
  • The asides on programming-language history — Brendan Eich’s ten-day JavaScript hack (ch. 3), Wirth’s p-code lineage (ch. 2), the Ritchie “declaration reflects use” critique (ch. 3), the Pratt parser’s “oral tradition in industry” status (ch. 17). Nystrom uses these to ground the technical material in the people who actually built the artefacts.
  • The hand-drawn diagrams (Nystrom illustrated the book himself) — argument-flow diagrams in ch. 2, the open-vs-closed upvalue diagram in ch. 25, the tri-colour GC state diagram in ch. 26 — work pedagogically in ways the note does not.
  • The actual experience of typing clox into existence and watching it run a Fibonacci benchmark 30× faster than jlox. The 30× number is in this note; the feel of the speedup is not.
